# RG-380: historic Job Diary read paths

Research date: 20 October 2026
Method: current first-party ServiceM8 developer documentation, public ServiceM8 community guidance, and the separately documented Royal Glass staging source inventories; no additional Royal Glass app API probe in this research note.

## Finding

No documented read-only OAuth endpoint found that lists the **complete historic Job Diary** or establishes the exact timestamp and stable Diary-item ID of the visible **Job Created** and **Service** entries. This is a documentation finding, not proof that ServiceM8 has no internal or separately supported read path. The [ServiceM8 API index](https://developer.servicem8.com/llms.txt) lists a Diary **create** endpoint, while its [Diary guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) explicitly says that capability cannot list or retrieve Diary items, including items the add-on created. Do not call `GET /diary.json` on the assumption that POST implies GET.

## Hosted MCP Diary feasibility check, 20 October 2026

ServiceM8's [MCP connection guide](https://support.servicem8.com/help-center/tips-trick-more/more/how-to-connect-servicem8-to-chatgpt-with-mcp) explicitly offers a **read Job Diary** action through its hosted MCP server at `https://api.servicem8.com/mcp`. This is a real historical Diary read through the separately connected ServiceM8 account; it is not the add-on's existing REST OAuth grant or evidence that the Office Assistant can reuse the connected chat's credentials. The public guide describes each ChatGPT/Claude user authorising a connection, but does not publish the `get_job_diary` response contract, a staff-impersonation mechanism, read-only tool permissions, completeness/pagination guarantees, or an add-on integration contract.

Unauthenticated, read-only protocol discovery returned HTTP 401 with a Bearer challenge from `POST /mcp` that names ServiceM8's [MCP protected-resource metadata](https://api.servicem8.com/PluginMCPServer_OAuthProtectedResource) and requires scope `mcp`. That metadata advertises the specific resource `https://api.servicem8.com/mcp`, scopes `mcp` and `mcp_client`, and authorization server `https://go.servicem8.com/`. Its [authorization-server metadata](https://go.servicem8.com/.well-known/oauth-authorization-server) advertises authorization-code and refresh-token grants, PKCE (`S256` and `plain`), a token endpoint and a dynamic client registration endpoint. The generic `/.well-known/oauth-protected-resource/mcp` location also responds but names the broader API root, so the challenge-linked metadata is the relevant MCP resource description. These facts prove an OAuth-protected MCP endpoint exists; they do **not** prove the add-on's existing ten-scope REST token works there, that either MCP scope is read-only, or that the MCP connection can be bound to the staff member who launched this add-on. No registration, consent, token request or authenticated MCP call was made by the app.

A read-only `get_job_diary` check of the four owner-approved Jobs returned 6 entries for R260766, 18 for R260609, 45 for R260611, and 68 for R260445. R260766 had 3 entries in the earlier UI/connector snapshot; that difference may reflect later Job activity and requires a contemporaneous UI check before claiming completeness. The R260609 and R260611 counts agree with the previously observed Diary inventories. The connected response identified Job Created and some status-change entries as `JobStatusChange`, with exact event times and an object UUID; R260445's Quote Approved event was at `2026-09-24 16:11:19`. It supplied no object UUID for R260609's Service entry, R260611's ten calls, or R260445's three calls. In all, 14/18, 39/45, and 53/68 entries respectively lacked an object UUID on those three Jobs. The entry-content field is named `content_preview`; no full-body, binary-file, next-page, or total-count contract was supplied. No customer content or raw IDs were saved in this note.

The [published REST index](https://developer.servicem8.com/llms.txt) and [create-only Diary guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) still do not document a historic `JobStatusChange` or complete Diary GET for the add-on. A read-only search of `D:\Royal Glass Dev\rgtools` found `/note.json` reads/writes labelled as Job Diary note handling, a Notes/Email conversation snapshot, and an account-key Inbox reconciliation that reads only the first 500 rows. The snapshot caps context at eight notes (300 characters each), four emails (800 body characters each), then 4,000 serialized characters overall; its quote workflow can mark a Notes/Email/file result partial. This may support a clearly labelled **conversation or notes summary**, but cannot prove a whole-Job history. The rgtools search found no complete Diary reader or staff-bound MCP adapter to reuse. The hosted MCP path is therefore a separate architecture candidate. Proving it for Office Assistant requires its own per-staff OAuth connection and a bounded test of Job access, response completeness, full contents, pagination and denied access; do not substitute the chat connection for those checks.

The [MCP primary-source check](./rg380-mcp-primary-source.md) records the published connection and protocol evidence separately from the live Job comparison.

## Decision for this slice

Keep the RG-380 full-Diary and Job-answer gate closed. The three Jobs already probed through the staging app, plus the separately inspected R260445, do not resolve all Diary item IDs/timestamps or body/file parity. The [Diary create-only guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) explicitly rules out using its POST capability as a read path. The [Inbox list reference](https://developer.servicem8.com/reference/listinboxmessages) includes `phone_call` and `converted_to_job_uuid`, but documents no Job UUID filter; a [ServiceM8 community reply](https://community.servicem8.com/t/accessing-outbound-sms-message-body-for-specific-job-uuids-crm-sync/1054) confirms no supported Job UUID query for that list. Reading the whole account Inbox to investigate one Job would expand the privacy and pagination scope, and even then might not cover all Job Diary calls. Do not add `read_inbox` merely on the assumption that it solves R260611's ten call entries.

Ask ServiceM8 to confirm whether an **approved, read-only OAuth** historical Job Diary path includes Job Created, Service, call and status-change rows, with exact Diary timestamps, stable row UUIDs, Job linkage and staff-impersonation semantics. The [Job Admin Activity reference](https://developer.servicem8.com/reference/listjobadminactivities) does not answer this; its documented scope describes administration time records. ServiceM8's [support guidance](https://support.servicem8.com/questions/integrations/does-servicem8-provide-support-for-custom-development-or-the-api-and-sdk) says API development is self-serve and points to the public developer community for questions; any public post must use synthetic examples and no account, staff or customer identifiers. No external question has been sent. If a supported path is identified, add it only after a scoped implementation and same-staff UI/API parity check.

## Draft question for the developer community (not posted)

> We are building a read-only OAuth Add-on that must reconcile everything a staff member can see in one Job Diary before generating a Job summary. The documented Note, Email, SMS, JobActivity, Attachment, FormResponse and JobPayment reads cover some item types. Your hosted MCP `get_job_diary` tool also returns historic Job Created, Service, call and status-change entries, but its public guide does not state whether a custom add-on can connect each signed-in staff member to that read-only tool, or obtain full content and complete pagination. Is that supported? If so, what authentication flow, tool permissions, staff access semantics, full-content fields and pagination contract apply? If the intended add-on path is REST instead, is there a supported historical Diary or `JobStatusChange` read with stable IDs, exact event times and Job links under `x-impersonate-uuid`? Please confirm any limitation so the add-on can keep its Job-summary feature disabled when coverage is incomplete.
