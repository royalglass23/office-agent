# RG-380: historic Job Diary read paths

Research date: 20 October 2026
Method: current first-party ServiceM8 developer documentation, public ServiceM8 community guidance, and the separately documented Royal Glass staging source inventories; no additional Royal Glass app API probe in this research note.

## Finding

No documented read-only OAuth endpoint found that lists the **complete historic Job Diary** or establishes the exact timestamp and stable Diary-item ID of the visible **Job Created** and **Service** entries. This is a documentation finding, not proof that ServiceM8 has no internal or separately supported read path. The [ServiceM8 API index](https://developer.servicem8.com/llms.txt) lists a Diary **create** endpoint, while its [Diary guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) explicitly says that capability cannot list or retrieve Diary items, including items the add-on created. Do not call `GET /diary.json` on the assumption that POST implies GET.

## Decision for this slice

Keep the RG-380 full-Diary and Job-answer gate closed. The three approved Jobs' source inventories do not resolve all Diary item IDs/timestamps or body/file parity. The [Diary create-only guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) explicitly rules out using its POST capability as a read path. The [Inbox list reference](https://developer.servicem8.com/reference/listinboxmessages) includes `phone_call` and `converted_to_job_uuid`, but documents no Job UUID filter; a [ServiceM8 community reply](https://community.servicem8.com/t/accessing-outbound-sms-message-body-for-specific-job-uuids-crm-sync/1054) confirms no supported Job UUID query for that list. Reading the whole account Inbox to investigate one Job would expand the privacy and pagination scope, and even then might not cover all Job Diary calls. Do not add `read_inbox` merely on the assumption that it solves R260611's ten call entries.

Ask ServiceM8 to confirm whether an **approved, read-only OAuth** historical Job Diary path includes Job Created, Service, call and status-change rows, with exact Diary timestamps, stable row UUIDs, Job linkage and staff-impersonation semantics. The [Job Admin Activity reference](https://developer.servicem8.com/reference/listjobadminactivities) does not answer this; its documented scope describes administration time records. ServiceM8's [support guidance](https://support.servicem8.com/questions/integrations/does-servicem8-provide-support-for-custom-development-or-the-api-and-sdk) says API development is self-serve and points to the public developer community for questions; any public post must use synthetic examples and no account, staff or customer identifiers. No external question has been sent. If a supported path is identified, add it only after a scoped implementation and same-staff UI/API parity check.

## Draft question for the developer community (not posted)

> We are building a read-only OAuth Add-on that must reconcile everything a staff member can see in one Job Diary before generating a Job summary. The documented Note, Email, SMS, JobActivity, Attachment, FormResponse and JobPayment reads cover some item types, but we cannot establish a supported historical read for Job Created, Service, call and status-change entries. Is there a supported read-only OAuth resource that returns these existing Diary events with stable IDs, exact event times and Job links under `x-impersonate-uuid`? Does `jobadminactivity` include any of these event types, or only administration time records? For call entries, is there a Job-scoped read that covers calls placed before and after Job creation? The InboxMessage list has no documented Job UUID filter, so an account-wide scan would be disproportionate. If these historic entries are unavailable through the supported API, please confirm that limitation so the Add-on can keep its Job-summary feature disabled.
