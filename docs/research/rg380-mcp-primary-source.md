# RG-380: ServiceM8 MCP primary-source check

Checked 20 October 2026. This note uses only ServiceM8's public documentation, unauthenticated OAuth discovery responses, and the ServiceM8 connector's published tool declaration. No Job data, credentials, token or customer content was read for this check.

## What is established

- ServiceM8 hosts an MCP server at `https://api.servicem8.com/mcp` and advertises reading Job Diary entries, activities and notes through a connected ChatGPT or Claude client. Its [connection guide](https://support.servicem8.com/help-center/tips-trick-more/more/how-to-connect-servicem8-to-chatgpt-with-mcp) describes a ServiceM8 sign-in and authorisation; for Claude Team/Enterprise, each user connects after an owner adds the server. This proves a per-user *connector* authorisation flow exists. It does **not** establish that an external ServiceM8 add-on can reuse its own REST grant to call MCP or that an MCP connection impersonates the staff member who launched the add-on.
- The live unauthenticated [MCP protected-resource metadata](https://api.servicem8.com/PluginMCPServer_OAuthProtectedResource) names resource `https://api.servicem8.com/mcp`, scopes `mcp` and `mcp_client`, and authorisation server `https://go.servicem8.com/`. The live [authorisation-server metadata](https://go.servicem8.com/.well-known/oauth-authorization-server) advertises an authorisation-code/refresh-token flow, PKCE (`plain`, `S256`), a token endpoint and a client-registration endpoint. An unauthenticated `POST /mcp` returned `401` with a Bearer challenge requiring scope `mcp`. These are protocol discovery facts, not proof that the existing Office Agent `read_jobs ...` REST bearer token will be accepted by MCP. No client was registered and no OAuth flow was started.
- ServiceM8's [REST OAuth documentation](https://developer.servicem8.com/docs/authentication) explains that `x-impersonate-uuid` applies to OAuth API requests and restricts results to a staff member's permitted records. It does not mention MCP or list either `mcp` or `mcp_client` in its REST scope table. The [Add-on Types guide](https://developer.servicem8.com/docs/add-on-types) and [web-service hosted add-on guide](https://developer.servicem8.com/docs/web-service-hosted-add-ons) describe add-on OAuth and callbacks, but do not describe attaching an MCP authorisation to an add-on launch. The same header's support on `/mcp` is therefore **unknown**; do not assume REST impersonation carries over.
- The available ServiceM8 `get_job_diary` tool declaration accepts `job_uuid` or `job_number` and a connector `link_id`. Its declared result is `{job_uuid, entries[]}`, each entry with `timestamp`, `title`, `content_preview`, `icon`, `author`, and optional `object_type`/`object_uuid`. No page, cursor, total count, full-body or file-byte field appears in that declaration. This is a schema observation, **not** proof of a hard truncation limit or that entries are missing; it also cannot prove complete historical coverage. See ServiceM8's [MCP connection guide](https://support.servicem8.com/help-center/tips-trick-more/more/how-to-connect-servicem8-to-chatgpt-with-mcp) for the published Diary capability. The tool declaration was inspected without invoking it.
- The [ServiceM8 MCP developer page](https://developer.servicem8.com/docs/mcp-server) only links to the ChatGPT/Claude connection guide. It publishes no custom add-on integration contract or full `get_job_diary` response semantics. The [Diary posting guide](https://developer.servicem8.com/docs/posting-an-add-on-job-diary-item) remains create-only for REST add-ons and cannot serve as a historical read fallback.

## Decision for Office Agent

The hosted MCP endpoint is a **candidate separate connection**, not a verified replacement for the staff-bound REST audit. Public discovery suggests an MCP-specific OAuth grant is needed. Even after connecting, the published tool schema gives previews rather than documented full bodies and gives no completeness or file contract. Consequently RG-380's full-Diary and Job-answer gate should remain closed. No additional REST scope, MCP registration, credential transfer or Job read is justified by this research alone.

To change that verdict, obtain an add-on-specific, staff-bound MCP connection design and a safe staging proof: establish the actual grant and staff identity, confirm a denied Job stays denied, and reconcile every Diary row plus full text and files against the same staff's UI. If MCP cannot provide that, keep the existing fail-closed behavior. The owner declined a public community post; this note did not contact ServiceM8.
