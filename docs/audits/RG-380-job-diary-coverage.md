## Reproducible fixture and review procedure

1. Select synthetic Jobs, or record the owner's explicit authorisation for each real Job. Record account UUID and staff role in a restricted evidence store; use pseudonymous Job labels in this document. Include both an office coordinator and estimator, a wrong-staff case, and a wrong-account case. Do not copy customer bodies, files or tokens into Git.
2. In ServiceM8, have the staff reviewer enumerate **every** Diary item for each Job. Capture a restricted export or screenshot with the UI item type, source label, event time, body/file availability and a stable reviewer-assigned item key. Cover an inbound and outbound email/reply and SMS, call, changed booking, quote/version, invoice/payment, photo/file, form, note, creation and status event. A fixture missing a type cannot clear that type.
3. From the same signed staff and connected account, read the parent Job first. Record the returned Job UUID and the staff-visible match before any child read. A denied or mismatched parent stops the fixture. Do not use an API key, administrator token or another staff identity to fill a gap.
4. For each approved source, record the endpoint, granted scope, request time, HTTP result and pagination until the endpoint's end condition. Record each source ID, Job link, timestamp field and meaning, body or binary availability, duplicates and unreadable items. Follow `x-next-cursor` where documented; Inbox uses its own offset/limit contract. Keep the raw response only in the approved restricted location.
5. Match each UI item to API item(s) by stable IDs and content, not by count alone. Classify `matched`, `missing`, `duplicate`, `unreadable`, `scope denied`, `request failed`, `pagination incomplete`, or `no approved read path`. Never turn a denied/failed page into a zero count. Note any API-only item separately.
6. Have the office coordinator and estimator review the reconciled matrix. Record reviewer, date, fixture label, disputed matches and decision. The audit passes only when every relevant visible type has complete authorised content and a repeatable read path for both roles, with no blocking gap. Otherwise leave Job outputs closed and pass the exact gap to RG-381 or the access decision owner.

## Final summary-focused audit finding, 20 October 2026

The owner clarified that the Office Assistant's Job output should be one plain-language paragraph followed by short bullets for key Diary events. Staff do not need to see a source-ID matrix, raw message evidence, or file bytes in that output. Source IDs and UI comparisons are internal audit tools; a missing MCP object UUID alone does not block a useful summary. A photo or file may be described as added without interpreting its contents.

The staging MCP OAuth path returned `inventory_only` for R260609 (18 entries) and R260611 (45 entries), matching the earlier UI totals. A separate ServiceM8 connector read showed the expected Diary title categories, including R260609's Service and Job Created rows and R260611's ten calls and two status changes. The staging result provides no full text, published page/total contract, or verified MCP staff identity. Therefore a count or title match cannot establish that the app can read every event with enough detail to summarize what happened.

**RG-380 audit result: complete with a NO-GO finding.** The existing Job-answer gate remains closed; no summary, draft, or recommendation should be generated from this partial path. This closes the bounded coverage investigation, not the release dependency. RG-381 can implement the paragraph-and-bullets output only after a complete authorised read path and representative same-staff check are proven. The unresolved technical gaps are MCP staff identity/access semantics, complete event pagination, and event detail beyond truncated previews (with per-source REST enrichment where supported). No further count-only Job probe will clear these gaps.

## Exit decision

**Release verdict: NO-GO.** R260766, R260609 and R260611 are authorised fixtures, and the owner is the named reviewer. The first two staging route outputs prove the then-stored connection passed the exact eight-scope check and returned Notes, Email, Job Activity and Attachment metadata; the owner reported that source-inventory test looked good. R260611's staging output proves the ten-scope stored grant passed and all six source inventories completed, including SMS and payments. The owner qualitatively confirmed the SMS/payment comparison. However, R260611 has ten visible calls and two status changes, R260609 has a visible Service request, and all three Jobs have Job Created entries without confirmed matching historic reads from the staff-bound app. **One such unresolved relevant type is enough to reject a full-Diary coverage pass.** This is a decision about the current release gate, not a claim that ServiceM8 has no possible API path.

Further parity evidence remains outstanding: representative event-level and sufficient-text comparisons, a completed-Form fixture, wrong-staff and denied-source cases, and production grant/deployment state. File bytes are required only if the summary will make a claim about a file's contents. Production's last read-only connection check found an expired five-scope grant. A proposed CLI download of staging environment secrets was rejected by automatic approval review, so no direct staging database query was made. Keep the Job-answer code gate closed. A future supported historic read path and the outstanding same-staff checks are required before reconsidering a PASS or enabling any RG-381 full-Diary output. Asking ServiceM8 for clarification may resolve the path question but is not required to record this NO-GO result. This local audit document is not a Linear closeout or production release approval.
